## Rollback
Use the smallest step that fixes the problem.
1. **Turn v2 off:** promote `dpl_2ZTUrRtEVTd695RC5vCnBVeNVN73` (same code, v2 off), or run `vercel env rm V2_SHELL production` and redeploy. Users get the v1 dashboard. No data change.
2. **Code rollback to v1:** Vercel → Deployments → `dpl_E6AxrtutE5aGpix44hhXJFuuezHf` → **Promote**. The migrations are additive, and v1 runs on the migrated schema; this was rehearsed.
3. **Data restore (only if data is damaged):** restore from Neon branch `pre-v2-pilot-2026-10-17`.

### The legacy-key limitation, without restoring the database
When an account opens API credentials, v2 can move a project's SerpApi key into the encrypted account credential and clear the project's plain-text copy. v1 reads only the project copy. Before release only **two** projects had such keys: Wewine #17 and Jackalopehotels #3. After a code rollback (step 2), restore just those keys from the backup branch:

1. In Neon, copy two connection strings, both **unpooled**:
   - the backup branch `pre-v2-pilot-2026-10-17`
   - Production (the default branch)
2. Save them into `%USERPROFILE%\.seo-console\restore.env` as `BACKUP_DATABASE_URL="…"` and `TARGET_DATABASE_URL="…"`, using the same clipboard-to-protected-file method as the migration.
3. Dry run, which lists the projects that would be restored and never prints keys:
   ```
   npx tsx --env-file=%USERPROFILE%\.seo-console\restore.env scripts/restoreLegacySerpKeys.mts
   ```
4. Apply:
   ```
   npx tsx --env-file=%USERPROFILE%\.seo-console\restore.env scripts/restoreLegacySerpKeys.mts --apply
   ```
5. Delete `restore.env`.

The script only fills projects whose key is now empty and whose owner hasn't changed. Everything else stays as it is. The simpler alternative is to re-enter the key on those projects in the v1 Reviews settings.

**Never** delete or rotate `CREDENTIALS_ENCRYPTION_KEY` while encrypted credentials exist. Rolling back keeps it in place, and rolling forward again needs the same key.
